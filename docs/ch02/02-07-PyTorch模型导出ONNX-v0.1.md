## 2.7 PyTorch模型导出ONNX

　　模型训练完后，我们已经有了保存的权重。能否直接把它交给后续工具识别手写数字？本例的权重文件只保存参数，还需要对应的模型定义，才能还原从图片到分类输出的计算过程。

　　2.6节展示了同一计算如何用ONNX节点表达。本节把恢复好的PyTorch模型转换为ONNX文件，这个过程称为导出，不需要重新训练。我们先准备模型和样例输入，再生成文件，检查结构、接口与输出。文件生成后，还要在相同输入下比较输出，才能进一步判断导出前后是否一致。

　　本节使用图2.6.1对应的MNIST模型。以下代码在opset 17配套目录运行，使用`official_mnist/main.py`的`Net`和`模型/hzl.pt`。配套脚本、依赖和原始ONNX见[模型版本记录](../../02-onnx-baseline/docs/model-version.md#m02-005--27正文采用的opset-17基线)。

### 2.7.1 恢复模型状态

　　本例权重文件中的参数字典没有完整描述`forward()`。恢复模型时，需要先创建相同的`Net`，再加载权重：

```python
from pathlib import Path

import torch
from official_mnist.main import Net

weights_path = Path("模型/hzl.pt")
model = Net().cpu()  # 在CPU上创建原模型结构。
state = torch.load(weights_path, map_location="cpu", weights_only=True)
model.load_state_dict(state, strict=True)  # 参数键名和形状必须匹配。
model.eval()                             # 关闭Dropout的训练行为。
```

　　`Net`提供各层的定义和前向计算，`weights_path`指向本例的权重。加载时，`strict=True`检查参数名和形状是否匹配。该权重的8个参数张量可以装入此结构，识别结果还需使用图片检查。[记录：M02-005]

　　最后一行为什么还要调用`eval()`？本模型有两处Dropout，训练时随机丢弃部分特征，评估时直接传递输入。要导出用于推理的模型，就应先切换到评估模式。这也解释了图2.6.1中Dropout节点的省略。评估模式决定相关层的行为，“不计算梯度”则决定是否记录梯度计算，两者作用不同。仅使用无梯度上下文，不能代替`eval()`。[来源：S02-005；记录：M02-001]

### 2.7.2 定义样例输入

　　恢复模型之后，还要告诉导出器怎样调用它。一次输入一张MNIST图片，对应的样例张量可以这样构造：

```python
example = torch.zeros(1, 1, 28, 28, dtype=torch.float32)  # NCHW固定形状。
```

　　这个形状与2.6节一致：1张图片、1个通道、28像素高、28像素宽。这里填零，是因为需要一个符合接口的样例来说明调用与形状，并不测试识别效果。零张量也不能证明前处理正确；后面比较模型输出时，需要另准备固定输入，让两边接收完全相同的数值。

　　本节采用的接口见表2.7.1。

<p align="center">表2.7.1 本例导出接口</p>

| 字段 | 输入 | 输出 |
| --- | --- | --- |
| 名称 | input | output |
| 数据类型 | float32 | float32 |
| 形状 | [batch,1,28,28] | [batch,10] |
| 含义 | 按训练约定前处理的一批MNIST灰度图 | 每张图片的10类对数概率 |

　　接口名称由导出脚本设置，形状和类型已经从实际ONNX文件读取。[记录：M02-005]

　　输入输出名称是图接口的标签，后续工具可以据此找到对应张量。本例的输出名为`output`，其含义由模型末端的LogSoftmax确定。每张图片对应10个对数概率。

### 2.7.3 选择导出设置

　　opset该选哪个版本？要看接收模型的运行时或编译器支持哪些算子规则。[来源：S02-005] 本节沿用已做CPU对照的opset 17基线。面向具体设备，还需查阅对应的软件开发工具包（software development kit，SDK）和转换工具的支持范围。

　　面向具体工具时，可按表2.7.2逐项核对。该表说明核对方法，不替代指定SDK的官方支持依据。

<p align="center">表2.7.2 导出设置与目标工具核对表</p>

| 需要核对什么 | 为什么要核对 | 记录什么 |
| --- | --- | --- |
| 芯片、SDK和转换工具版本 | 同一平台不同版本的支持范围可能不同 | 官方支持表的版本与位置 |
| 模型opset及实际算子 | 支持某个opset并不自动证明所有算子属性都适用 | 算子及属性限制 |
| 输入形状（shape）、数据类型（dtype）和布局（layout） | 工具可能要求固定尺寸或特定接口形式 | 实际使用的输入约定 |
| 动态维度及其取值范围 | 模型与工具可能只支持部分动态情形 | 允许变化的轴及约束 |

　　本例用单张图片的形状作为导出样例，并通过`dynamic_axes`将输入和输出的第0维都标为`batch`。实际输入的图片张数可以变化，通道数和高宽仍为1、28、28。若改变高宽，展平后的特征数量还要满足全连接层要求。

　　本例使用PyTorch 2.4.1的传统导出接口。其他导出路径可能使用`dynamic_shapes`，应按所用版本和导出路径选择参数。[来源：S02-005；记录：M02-005]

### 2.7.4 导出与保存

　　准备好模型、样例输入和导出设置后，调用导出接口：

```python
onnx_path = Path("mnist_cnn.onnx")
torch.onnx.export(
    model,
    example,
    str(onnx_path),
    input_names=["input"],
    output_names=["output"],
    opset_version=17,
    dynamic_axes={"input": {0: "batch"}, "output": {0: "batch"}},
)
```

　　`torch.onnx.export()`将模型的计算映射为ONNX节点，并写入`onnx_path`。图2.6.1展示了这套导出设置下的节点，其中PyTorch的展平对应ONNX的Flatten，两处评估模式下的Dropout被省去。[记录：M02-005]

　　这里将新导出的文件保存为`mnist_cnn.onnx`。复验发布包中的原件时，将`onnx_path`指向`模型/hzl.onnx`即可。

### 2.7.5 核对导出结果

　　文件生成后，还需要检查结构、接口和数值。第一层检查文件是否符合ONNX的结构规则：重新读取磁盘上的文件，再调用ONNX checker。

```python
import onnx

exported = onnx.load(onnx_path)  # 读取磁盘上保存的模型。
onnx.checker.check_model(exported)
```

　　当前产物已经使用ONNX 1.23.2重新读取并完成此检查。读取文件还可以得到生产者PyTorch 2.4.1、IR版本8、ai.onnx opset 17，以及主图的10个节点。这些都是已保存文件的实际信息。[记录：M02-005] 不过，checker检查的是结构规则，还没有拿图片执行模型，不能由此推断识别结果或目标硬件兼容性。[来源：S02-006]

　　第二层是接口检查。实际读取的输入为`input`、FLOAT、`[batch,1,28,28]`，输出为`output`、FLOAT、`[batch,10]`。其中FLOAT在本例表示float32。这些字段与表2.7.1一致。Netron还可以辅助查看连线、属性和末端LogSoftmax，但它不能替代checker或数值比较。

　　第三层是数值回归：即使结构和接口符合预期，也要使用固定输入，检查转换前后的输出是否在约定范围内一致。[来源：S02-008] 可以先保存一份经过前处理的输入张量，再把完全相同的数值分别提供给PyTorch与ONNX执行后端，排除各自读图或归一化造成的输入差异。

　　本例的训练前处理包括ToTensor，以及均值0.1307、标准差0.3081的归一化。用于真实图片对比时应沿用这一约定，同时保持float32、NCHW和相同批次；具体执行ONNX的接口留到2.8展开。[记录：M02-001]

　　比较时先看输出形状是否相同、数值是否有效，再查看10个对数概率及最大值所在类别。两边预测出同一个数字，只能说明类别一致，不能说明各项数值足够接近：两组数值即使相差较大，最大值的位置也可能相同。

　　对每个输出元素，记PyTorch参考值为$a$，ONNX对比值为$b$，则绝对误差$e_{\mathrm{abs}}$为

$$
e_{\mathrm{abs}}=|b-a|
$$

　　当$a\ne0$时，相对误差$e_{\mathrm{rel}}$可以定义为

$$
e_{\mathrm{rel}}=\frac{|b-a|}{|a|}
$$

　　参考值为零时，相对误差的上述定义不适用；接近零时，该比值也可能放大很小的绝对差异。因此，应同时报告绝对误差，并明确相对误差的零值处理规则。容许误差应在比较前依据任务要求约定，不把某次观察值临时当成“通过标准”。

　　实际判断时，可以把绝对容差与相对容差结合起来。设绝对容差为$t_{\mathrm{abs}}$、相对容差为$t_{\mathrm{rel}}$，要求每个元素满足

$$
|b-a|\leq t_{\mathrm{abs}}+t_{\mathrm{rel}}|a|
$$

　　右侧第一项照顾参考值为零或接近零的情况，第二项随参考值的大小调整允许差异。这个判据不需要除以参考值，但仍要先检查两侧形状相同、所有数值有限。通过检查只说明所选输入在这组容差下保持一致，不能代替整个测试集的准确率评估，更不能证明板端执行结果。

　　配套的`模型工具.py`先检查输出形状，再以PyTorch输出`reference`为参考，与ONNX Runtime输出`actual`比较。它将两侧输出转换为float64计算差值，并用原始float32输出和预先约定的容差进行判断：

```python
import numpy as np

error = np.abs(actual.astype(np.float64) - reference.astype(np.float64))
passed = np.allclose(actual, reference, atol=1e-5, rtol=1e-4)
```

　　原实验使用MNIST测试集索引0至9的10张图片，按前述方法归一化后，组成形状为`[10,1,28,28]`的一批输入。两侧分别用PyTorch 2.4.1和ONNX Runtime 1.20.1在CPU上运行，均得到形状为`[10,10]`的输出。10张图片的预测类别全部一致，100个输出值均满足联合容差，最大绝对误差约为$7.63\times10^{-6}$。[记录：M02-005]

　　原实验仅对参考值绝对值大于$10^{-6}$的元素统计相对误差。其中，测试集索引2的图片在类别1上的参考值约为$-3.70\times10^{-6}$，对应的绝对误差约为$1.19\times10^{-7}$，相对误差约为3.23%。参考值很小，因此绝对差异虽小，相对误差仍可能达到几个百分点。其余4个参考值接近零的元素单独检查了绝对误差。[记录：M02-005]

　　样本索引、标签、两侧完整输出及判定保存在[模型版本记录](../../02-onnx-baseline/docs/model-version.md#m02-005--27正文采用的opset-17基线)所列的历史实验文件中。这个结果只覆盖上述10张图片。若更换权重、导出设置或输入处理，应使用同一组输入重新执行对比。

### 2.7.6 管理模型版本

　　假设后来又导出了一次模型，文件名仍叫mnist_cnn.onnx。怎样知道它与第一次是否相同？仅凭文件名无法区分，需要比较文件校验值，并找到生成它的模型定义、权重和导出脚本。本例已将这些材料关联记录，同时保存了源码、权重和ONNX的SHA256，完整值见配套版本记录。

　　保留原始文件后，还可以研究模型简化。在满足等价条件时，可以提前求出只依赖常量的计算结果。这称为常量折叠，是一种可能生成派生模型的图优化方法。ONNX Simplifier是候选工具之一，当前尚未选定其发行版或生成简化结果。[来源：S02-009] 派生模型仍需重新核对结构、接口与数值。

　　本例文件可按表2.7.3管理，位置相对opset 17配套目录。

<p align="center">表2.7.3 模型材料与派生关系</p>

| 材料 | 配套目录内位置 | 记录要求 |
| --- | --- | --- |
| 模型定义 | official_mnist/main.py | 源码版本、校验值 |
| PyTorch权重 | 模型/hzl.pt | 来源、校验值及结构匹配记录 |
| 导出脚本 | 02_07_导出与基线推理.py | 参数、依赖和执行说明 |

　　表中最后一行是保存约定，不表示已经存在派生文件。权重和ONNX保存在本地忽略目录，Git保存源码、说明和可共享记录。

　　无论是简化、固定输入尺寸，还是修改算子，得到的都是需要重新检查的新模型。应另存文件，再执行结构检查、接口核对和同输入数值回归。旧模型的对比结果不能直接用来证明新模型正确。

　　导出后，应保留接口明确、版本可追溯的ONNX文件及回归记录。下一节将进一步展开ONNX Runtime的使用，建立可复用的基线推理。面向具体芯片时，还要按照对应SDK核对算子和形状支持；PC上的结构检查与数值回归不能替代板端验证。
